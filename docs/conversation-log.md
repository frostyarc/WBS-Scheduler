# WPS 진행관리 — 대화 기록 (2026-08-11 ~ 2026-08-12)

WPS 스케줄링 웹앱을 처음 기획하고 배포까지 진행한 대화의 요약 기록.

## 1. 프로젝트 시작 (08-11)

Notion으로 팀 WPS(작업진행) 트래커를 만들까 하다가, 노션을 새로 배우는 부담과 유료 DB 제약 때문에 바이브 코딩으로 직접 웹사이트를 만들기로 결정.

**요청한 핵심 기능 3가지**
1. 일정 등록 — 작업 이름, 작업 구분(PLC/전장/기구/SCADA/디지털트윈), 시작일~종료예정일, 작업현황(준비중/작업중/작업완료, 초과 시 표시), 작업설명
2. 프로젝트 모니터링 — 파트별 진행도(막대그래프), 전체 진행도(원 그래프)
3. 개인별 일별 보고서 — 날짜 클릭 시 블로그 포스팅 형태로 제목/작성시간/내용/첨부파일

**그 자리에서 물은 질문**: Netlify로 배포하면 여러 명이 실제로 읽고 쓸 수 있는지, Supabase가 뭔지, 팀 내부용으로 보안 이슈는 없는지.

**답변/조치**
- Netlify는 정적 파일 호스팅만 하므로, 여러 명이 데이터를 공유하려면 Supabase(무료 Postgres DB + Storage) 같은 백엔드가 필요하다고 설명.
- Supabase 무료 티어 개념(로그인/DB/파일저장 대신 서버를 직접 안 만들어도 되는 서비스) 설명.
- 보안: RLS(Row Level Security)를 켜지 않으면 anon key를 아는 누구나 DB에 직접 접근 가능하니, 로그인 + RLS를 권장.
- **베타 데모**를 Claude Artifact로 먼저 제작 — 브라우저 localStorage만 쓰는 단일 HTML 파일로, UI/UX 피드백용. (실제 배포판이 아님)

## 2. 베타 피드백 반영 (08-11)

디자인에 만족 후 5가지 추가 요청:

1. 등록된 일정을 **날짜별 / 파트별 / 멤버별 / 상태별** 4가지 방식으로 볼 수 있게
2. 글씨 크게, 특히 날짜가 눈에 잘 들어오게
3. 마감 전엔 `D-1`, 마감 초과 시 `D+1` 형태로 디데이 표시
4. 일정 **수정** 기능 추가, 일별보고서도 **수정/삭제** 가능하게
5. "남의 것은 못 건드리게" 하려면 어떻게 구현하는 게 좋을지 의견 요청

**권한(5번) 관련 조언**: 글마다 개별 코드 입력은 비추천(잊어버리면 복구 불가, UX 번거로움). 대신 "팀장 모드(마스터코드) + 이름 매칭" 2단 구조를 제안 — 다만 이건 클라이언트 JS 검증이라 실수 방지용이지 진짜 보안은 아니라고 명확히 설명. 이 방향으로 베타에 구현.

## 3. 배포판 전환 (08-11)

> "팀원들 다 나쁜 마음 먹을 사람들 아니라고 믿고 그냥 쓰게 하자. 5번은 패스."

권한 기능(팀장모드/마스터코드)을 전부 제거하기로 결정 — 신뢰 기반 운영. 동시에 "유지보수 가능하게(내가 아니라 네가), 베타 말고 바로 배포판으로" 요청.

**한 일**
- localStorage 데모를 실제 Supabase 연동 정적 웹앱으로 전면 재작성.
- 파일을 역할별로 분리: `index.html`(마크업) / `css/styles.css` / `js/config.js`(Supabase 접속정보) / `js/supabaseClient.js` / `js/data.js`(Supabase 호출을 모은 유일한 파일) / `js/util.js`(공용 상수·헬퍼) / `js/schedule.js` / `js/monitor.js` / `js/report.js` / `js/app.js` / `supabase/schema.sql` / `README.md`.
- `supabase/schema.sql`: `tasks`, `posts` 테이블 + RLS 정책(로그인 없이 전체 허용) + `attachments` 스토리지 버킷, 재실행 가능하게 작성.
- Supabase 설정 가이드 제공: SQL Editor에 schema.sql 실행 → Project Settings·API에서 URL/anon key 복사해 `config.js`에 채우기 → Netlify에 폴더 드래그로 배포.

## 4. 데이터 확인/내보내기, 이름 필드 정리 (08-11)

- **Q**: Supabase에서 데이터 확인 가능? 파일로 저장 가능?
  **A**: Table Editor에서 확인 가능. 앱에 **CSV 내보내기** 버튼 추가(일정등록 탭: 현재 필터링된 목록 / 일별보고서 탭: 전체 기록), 한글 깨짐 방지용 UTF-8 BOM 처리.
- 상단 우측 "이름" 입력창 제거 요청 (일정/보고서 등록 시 이미 이름을 쓰니 불필요) — 동시에 일별보고서 작성 폼에 원래 **작성자 입력란이 없었던 버그**를 발견해 추가, 수정 시 작성자도 바꿀 수 있게 고침. `담당자`/`작성자` 필드를 필수 입력으로 변경.
- **Q**: Supabase 무료 플랜 데이터/파일 용량 한도는?
  **A**: 웹서치로 확인 — DB 500MB, 파일저장 1GB, 파일 1개 최대 50MB, 월 전송량 5GB, 7일 미접속 시 프로젝트 일시정지, 무료 프로젝트 최대 2개.

## 5. 모니터링 = 종합관제실 개편 (08-12)

모니터링 탭이 미흡하다는 피드백. 요청 8가지:

1. **HOME** 버튼 → 전체 진행도(도넛+파트별 바) 화면으로.
2. **총 작업** 클릭 → 전체 일정 체크리스트(읽기 전용), 시작일 최신순.
3. **작업완료** 클릭 → 완료 체크리스트, 종료예정일 최신순.
4. **작업중** 클릭 → 마감 지났으면 오래 지연된 것부터, 안 지났으면 D-day 임박한 것부터.
5. **지연** 클릭 → 지연 체크리스트, 가장 오래 지연된 게 맨 위.
6. 새 작업 등록 폼을 기본 **접힌 상태**로.
7. 보기모드 줄 우측에 **자세히보기/간단히보기** 토글 추가.
8. 담당자는 작업이름 옆, 날짜는 작업구분 옆으로 배치해 카드 높이 축소.

**구현**: `monitor.js`에 `view` 상태(home/total/done/doing/overdue)와 `byDate(key, dir)` 정렬 헬퍼 도입 — 작업중/지연 뷰는 둘 다 `end_date` 오름차순 정렬로 통일하면 "지연 오래된 것 → D-day 임박한 것" 요구사항이 자연스럽게 한 기준으로 처리됨을 확인. 읽기 전용 `<table>` 체크리스트 뷰 추가. 일정등록 폼은 `<button>` 토글 + `hidden` 속성으로 접고 펼치게 처리(수정 버튼 클릭 시 자동 펼침). 자세히/간단히 토글과 레이아웃 압축 착수.

## 6. GitHub "빌드 과정" 오해 해소 (08-12)

> "빌드 과정이 없다는게 뭐임? 구버전 신버전 구분 안하겠다는거임?"

**설명**: "빌드 과정 없음"은 React 등 프레임워크 코드를 브라우저용 HTML/JS로 변환하는 컴파일 단계가 없다는 뜻일 뿐, 버전 관리와는 무관. 이 프로젝트는 이미 순수 HTML/CSS/JS라 변환할 게 없음. 버전 구분은 **git 커밋 기록**(모든 시점이 영구 보존, 되돌리기 가능) + **Netlify 배포 기록**(배포마다 스냅샷, 클릭 한 번으로 롤백)으로 이미 커버된다고 안내. 필요하면 git 태그로 v1.0 같은 이름도 붙일 수 있다고 제안.

## 7. GitHub 연결 & 비밀값 점검 (08-12)

`https://github.com/cpf21a2019114015/WPS-Scheduler.git`에 코드를 올리고, 앞으로도 코드를 맡기고 싶다는 요청 + `.env`/service_role 키가 커밋에서 반드시 빠지는지 확인해달라는 요청.

**한 일**
- `.env`, `secret` 파일 존재 여부 검색 → 없음 확인. 코드 전체에서 `service_role` 언급 검색 → "쓰지 말라"는 주석 한 줄뿐, 실제 사용 없음 확인.
- `.gitignore` 작성(`.env*`, `*secret*`, `*service_role*` 등 패턴).
- `git init`, 로컬 identity 설정, 첫 커밋, `git remote add origin`, `git push`.
- push 시 GitHub이 저장소가 **`frostyarc/WPS-Scheduler`로 이동**했다고 안내 → remote URL 갱신.
- `js/config.js`의 Supabase anon key는 의도적으로 그대로 커밋함(anon key는 원래 브라우저에 노출되는 공개 키이며 RLS가 실제 방어선이라고 설명; 진짜 위험한 service_role 키는 프로젝트에 존재하지 않음).
- Netlify GitHub 연동 절차 안내: Netlify → "Import an existing project" → "Deploy with GitHub" → 저장소 선택 → Build command 비움 / Publish directory `.` → Deploy. 이후 `git push`할 때마다 자동 재배포.

## 8. 레이아웃 미세조정 + 상태변경 UI 정리 (08-12)

세 가지 마지막 조정:

1. 날짜/담당자가 줄 오른쪽 끝으로 밀려있던 것 → `justify-content: space-between`을 `flex-start`로 바꿔 **파트명 옆에 날짜, 작업이름 옆에 담당자**가 바로 붙게 수정. (특별히 긴 텍스트 대비용 조치는 아니었음을 확인 답변)
2. 간단히보기가 "내용만 가리고 가로 폭은 그대로"였던 문제 → 실제 **M×N 카드 그리드**(`grid-template-columns: repeat(auto-fill, minmax(230px,1fr))`)로 재구성. 카드에는 작업이름/구분/날짜/담당자/현황/D-day/수정/삭제만 표시.
3. 각 일정 옆 상태 변경 드롭다운 제거 → 상태 변경은 이제 **"수정" 버튼 → 폼에서 변경**하는 흐름으로 통일.

**표준 워크플로 확정**: 앞으로 `wps_scheduler` 코드를 고칠 때마다 사용자가 요청하지 않아도 항상 `git add`/`commit`/`push`까지 자동으로 수행하기로 합의.

## 최종 상태 (2026-08-12 기준)

- **저장소**: `https://github.com/frostyarc/WPS-Scheduler`
- **배포**: Netlify(정적 호스팅) + Supabase(Postgres/Storage), GitHub 연동으로 push 시 자동 재배포 예정
- **폴더 구조**
  ```
  wps_scheduler/
    index.html
    css/styles.css
    js/
      config.js         Supabase URL/anon key
      supabaseClient.js
      data.js            Supabase 호출을 모은 유일한 파일
      util.js            공용 상수/헬퍼(파트·상태·D-day·CSV 등)
      schedule.js         일정등록 탭
      monitor.js          모니터링 탭(HOME + 체크리스트 드릴다운)
      report.js           일별보고서 탭
      app.js              탭 전환/초기화
    supabase/schema.sql   테이블 + RLS + 스토리지 버킷
    docs/conversation-log.md  (이 문서)
    README.md
  ```
- **권한 모델**: 로그인 없음, 이름은 표기용일 뿐 접근 제어 없음(신뢰 기반, 팀장 전용 기능 없음).
- **상태 변경**: 수정 폼을 통해서만 가능(인라인 드롭다운 없음).
